Chapter 7Satellite passes, search periods and the area limit

Two questions come up in every demonstration: "why was no 'after' image found?" and "why can I not check a bigger area?". This chapter answers both from the code and from measured runs.

7.1 How AegisEO searches for and chooses images

Every check has two date ranges, the 'before' search and the 'after' search (Section 4.5). For a case study they are fixed by hand; otherwise they are suggested from the event date by default_windows in backend/aegis/jobs.py: the 'before' search covers the 45 days before the event, and the 'after' search covers the event day and up to 12 days after it (never beyond today). For each satellite type, the data-acquisition agent (DataAcquisitionAgent in backend/aegis/agents/specialists.py) then:

  1. Searches the STAC catalogue of Planetary Computer for all images intersecting the area within the range. For optical images, scenes with 80% or more cloud over the whole satellite tile are excluded already in the search.
  2. Groups the results into passes. One satellite pass can be delivered as several files (tiles or slices); files from the same satellite, day, orbit number and direction are combined into one acquisition.
  3. Keeps only passes that cover at least 50% of the area (MIN_COVERAGE), so a pass that just clips the edge is ignored.
  4. Chooses with documented rules: for radar 'after', the earliest pass (rule P1: closest to the event, unaffected by cloud); for radar 'before', the latest pass from the same relative orbit and direction as the 'after' pass (rule P4), looking up to 24 extra days back if needed, so that both images share the same viewing angle; for optical, the three least cloudy candidates are examined and the cloud over the exact area is measured from the scene classification layer, then the clearest is chosen with a small penalty per day of distance (rule P2).
  5. Extends the 'after' search automatically if a satellite type has no usable pass at all: the end date is moved 7 days later, at most twice, and never past today (rule P3). Each decision is written to the record with its reason.
Real exampleIn 2022 only Sentinel-1A was working (Sentinel-1B had failed in December 2021), so each radar track repeated every 12 days: 4, 16 and 28 June on track 42. A second, overlapping track added passes on 7 and 19 June and 1 July, so a radar image existed every 3 to 9 days. AegisEO used track 42 on 28 June (before) and 27 August (after), giving identical viewing geometry. Optical images existed every 2-3 days; the clearest were 27 June and 31 August (100% cloud-free over the area).

7.2 Why an 'after' image may not exist

  • The satellite has not passed yet. With one radar satellite, the same place is imaged every 12 days on a given track (6 days with two). For an event 3 days ago there may be no 'after' radar image at all. The wizard warns when the event is less than 3 days old.
  • The pass was not recorded or not delivered. Satellite operators plan which regions are imaged on each pass, so not every theoretical pass becomes an image, and new images appear in the archive only after processing (typically within about a day for Sentinel-2 and within days for Sentinel-1 RTC).
  • The pass covers too little of the area (less than half).
  • Clouds hide the ground in optical images; for floods, radar still works, but for wildfires and landslides a clear optical pair is strongly preferred.

If no usable 'after' image remains after the automatic extension, safety check G04 stops the check with the status "No usable images", and the result page suggests making the 'after' search longer.

It was short but left a beginner guessing: what is a pass, why are there gaps, which end of the search to move, and would a longer search change the result? 7.4 The 120-day maximum and the 60-day gap

The longest allowed search is 120 days, for both 'before' and 'after'. The limit is enforced in three places that agree: safety check G03 on the server (the request is rejected), the date validation in the wizard (Continue is disabled with an explanation), and the API endpoint /api/config, from which the wizard reads the number. A long search makes it likely that the chosen image is far from the event; very long ranges mainly add images that would not be chosen anyway. Separately, if the 'before' and 'after' images end up more than 60 days apart, safety check G06 records a note, because over many weeks crops grow and rivers change with the seasons, and these normal changes can look like flooding or damage. The Sindh case study shows this note (65 days between the optical images).

7.5 The largest checkable area (1,500 km²)

What the limit is and where it is implemented

The limit is an application-level setting of the server: max_aoi_km2 = 1500.0 in backend/aegis/config.py, which an administrator can change with the environment variable AEGIS_MAX_AOI_KM2. (An environment variable is a named value given to a program when it starts, used here so settings can change without editing code.) It is enforced at four points:

WhereWhat happens above the limit
POST /api/analyses (routes_analyses.py) via AOI.validate_size (geo/aoi.py)HTTP 400: "AOI is too large (1760 km2); maximum is 1500 km2 per analysis. Split the area into smaller analyses." (message observed in a test on 8 Nov 2026)
POST /api/catalog/preview (routes_system.py)The archive check refuses the area (HTTP 400).
Safety check G02 (guardrails.py)The agent rejects the request before any tool runs.
The wizard (StepWhere, AoiPicker, draft.ts)The size badge says "Too big: zoom in" and Continue is disabled with an explanation.

It is not a restriction of the satellites or of the data provider: the STAC catalogue accepts any search box, and COG files can be read in windows of any size. It is a processing and quality budget chosen by the developer for a single computer.

Why the limit exists: what grows with the area

  1. Pixels and memory. Every layer of a check (radar and optical before and after, height, water, land cover, population, probability, uncertainty) is held in memory on one common grid. To bound memory and run time, the grid may have at most 2.6 million pixels (max_grid_pixels). At the default 20 m pixel size that is about 1,040 km²; a larger area forces larger pixels, in 10 m steps (rule P0 in Grid.for_aoi, backend/aegis/geo/grid.py).
  2. Detail. Larger pixels lose narrow features. The flood model was trained on 10 m images; at 30 m and beyond the inputs differ further from what it learned.
  3. Square size. At most 900 squares are ranked (max_cells in prioritize.py), so squares grow from 1 km to 1.5 km above 900 km² and to 2 km above about 2,025 km², and each priority then describes a larger area.
  4. Downloads. Downloading is most of a first check's time; at a fixed pixel size, data grow with the area.
  5. Public services. The OpenStreetMap request asks the Overpass server to give up after 90 seconds or 128 MB. Large boxes over dense cities are the most likely to fail, in which case the check continues without infrastructure data and says so.
  6. Shared capacity. One server runs two checks at a time; very large checks would hold a worker for longer.

The result is instructive. A 6.7 times larger area took only about 20% longer, because rule P0 switched to 30 m pixels and the grid grew only three-fold. The real price of a large area is therefore less detail (30 m pixels, 1.5 km squares), not waiting time, at least on a fast connection and in a rural area. (Run times vary with the network: the same 216 km² area took 625 s on 1 November.)

Can the limit be changed?

Yes, technically: an administrator can set AEGIS_MAX_AOI_KM2. Before this round of changes that would not have worked properly, because the web interface contained its own copy of the number (MAX_KM2 = 1500 in frontend/src/pages/check/draft.ts): raising the server limit would have left the interface refusing larger areas, and lowering it would have let the interface accept areas the server then rejected. That copy has been removed; the interface now reads the limit from the new endpoint GET /api/config, together with the minimum area, the pixel budget, the area that keeps full detail, and the date limits.

DecisionThe default limit was kept at 1,500 km². Raising it would trade detail for coverage: above about 2,340 km² pixels would become 40 m, squares 2 km and more, Overpass requests over dense regions would fail more often, and the flood model would see inputs further from its 10 m training data. For a larger region, several checks of up to 1,500 km² give better results. The interface now explains this (Figure 4.9) and warns, for areas above about 1,040 km², that 30 m pixels will be used.
