Chapter 14Testing, results, changes and limitations

This chapter reports how AegisEO was tested, the results of every test run while this report was prepared (8 November 2026), the changes made in this round, and the system's known issues and limitations. All numbers come from test output, the project's result files or the database of completed checks.

14.1 How AegisEO is tested

No single kind of test can show that a system like this works. Code can be correct while the model is inaccurate, and both can be fine while the interface misleads people. AegisEO is therefore tested at several levels, from single functions up to complete checks of real disasters:

LevelWhat it showsWhere
Backend unit and integration tests (pytest)Individual functions behave as specified (every safety-check threshold, the score formula, scene selection, grid building, the HTTP client's retries and cache), and whole checks on practice scenes end with the correct status, record and files. External services are replaced by stand-ins (mocks: fake versions that answer instantly and predictably), so the tests need no internet and always give the same result.backend/tests/ (10 files)
Live-network testThe real Planetary Computer catalogue answers a real search (Sentinel-1 passes over Sindh, 20 August - 5 September 2022). Run only on request, because it depends on the internet.test_net_sources.py
Frontend unit tests (Vitest)The plain-language texts use only numbers from the result, the wizard blocks exactly what the API would reject, components are accessible (values as text, not colour alone).*.test.ts(x) in frontend/src
End-to-end tests (Playwright)A real browser uses the real application: the home page, the wizard, date errors, coordinates search, and a complete practice check through to a review decision, on a desktop screen and on a phone-sized screen.frontend/e2e/
Static checksruff finds programming errors and bad patterns in Python; the TypeScript compiler checks that every value in the frontend has the type the code expects.whole code base
Flood-model evaluationHow well the trained model maps water compared with experts, under four sensor conditions, on images it never saw.models/evaluation.json

Real checks (acceptance runs)The complete system on real past disasters with real satellite images.Database of completed checks

14.3 Flood-model evaluation

The flood model was evaluated with python -m aegis.ml.evaluate on the Sen1Floods11 test split (90 image chips) and the Bolivia split (15 chips of a flood event that no training image comes from, which tests how well the model generalises to a new place). Each model was tested under four conditions: the images as they are; with simulated 50% cloud on the optical image; with no optical image at all; and with no radar image at all. The measure is IoU (intersection over union): the area that both the model and the experts marked as water, divided by the area that either of them marked; 1.0 is perfect agreement.

Further results for the deployed model on the test split:

  • F1 0.915, precision 0.932, recall 0.899. Precision is the share of pixels marked as water that really are water (few false alarms); recall is the share of real water that was found (few misses); F1 combines the two.
  • IoU 0.779 for flood water only, that is, excluding water that is permanently present (rivers and lakes are easier to map than new flooding). On Bolivia this value is 0.822.
  • Calibration: the expected calibration error (ECE, the average gap between the stated probability and how often it is right) is 0.006 for the deployed model; temperature scaling reduced it for the fusion model from 0.014 to 0.005.
  • Uncertainty is meaningful: the uncertainty of a pixel predicts whether the model is wrong there with an AUROC of 0.885 (0.5 would be useless, 1.0 perfect). Leaving out the 10% most uncertain pixels raises the accuracy from 97.5% to 99.4%.
What the table shows(1) Combining radar and optical beats either alone and beats every classical method. (2) Under cloud, the gated design and the radar specialist keep the result usable: 0.739 at 50% cloud, compared with 0.419 for the optical-only model. (3) Without any optical image the result falls to 0.653 on the test split and 0.520 on Bolivia, which is why AegisEO lowers its confidence and often asks a person in that situation. (4) The deployed combination was chosen on the validation split before these test numbers were computed, so the test and Bolivia results are fair estimates.

How to read these results:

  • Sindh and Palisades show clear, large changes with plausible exposure. The requests for review are the safety checks working as designed: Sindh's dry-season soil before the flood looks unlike anything in the training data (a genuine reason for a person to look), and the Palisades area was drawn tightly around the burn scar, so most of it really did burn.
  • Derna is an honest near-miss: after two dams failed on 10-11 September 2023, the water rushed through the city to the sea; the first "after" radar image was taken on 12 September at 16:30 UTC, about a day and a half later, and satellites can only see water that is still standing when they pass (the case study was included to show exactly this limit). AegisEO found almost nothing and said so, instead of inventing a flood. This is a real limitation for flash floods.
  • Wayanad shows how the system behaves with weak evidence: heavy monsoon cloud, low agreement between methods, Low confidence and several reasons to ask a person.
  • Run times: 5 to 10 minutes for a first check, mostly spent downloading image windows; seconds for a repeat. The size test (Section 7.5) took 189 s for 216 km² and 225 s for 1,450 km² on a faster connection.

These runs were also the source of one real bug, already described in Section 6.5: in the first runs, safety check G16 withheld every situation summary because of the "30" in the population source's name "(~30 m)". The check failed safe, and the list of known values was corrected (docs/failure_analysis.md).

14.8 Known issues and limitations

Limits of the method (they follow from physics or from the data):

  • Only the change visible at the satellite passes is seen: water that drains before a pass (flash floods) is missed, and the "after" image may be days old (Chapter 7).
  • Flood under dense trees and in narrow streets between tall buildings is hard to see with 10-20 m pixels and side-looking radar.
  • Flood depth, building damage and casualties are not estimated. "People potentially exposed" uses population estimates from 2015-2020 and says nothing about harm.
  • Only the flood method has a trained, evaluated model. Wildfire and landslide methods are standard index rules that were checked on case studies, not evaluated against expert maps; landslide results are always sent to a person.
  • The flood model was trained on 252 expert-labelled chips (446 in the whole dataset). Unusual landscapes (such as Sindh's dry soil) are flagged by G11 rather than handled confidently.
  • The training images (Sentinel-2 Level-1C, Sentinel-1 sigma-nought) are not exactly the same product as the images used in operation (Level-2A, terrain-corrected gamma-nought). The difference is reduced by conversion and training-time brightness variation (Section 13.2), not removed.
  • OpenStreetMap is incomplete in many regions, so "no hospital found" does not mean there is no hospital.

Known issues of the software (found during this review and not changed, because they are design decisions or outside this round):

  • The setting run_timeout_s (1,800 s) exists but is not used anywhere: a check has no overall time limit. Each request to an external service has its own timeout and retries, and a person can always press Stop. Similarly, AEGIS_MC_DROPOUT_SAMPLES does not change the number of uncertainty samples in a check: the value from the request (default 6, Section 8.3) is always used.
  • Checks run in two worker threads inside the server process. This suits one server; several servers would need a shared job queue. If the server restarts, running checks are marked "interrupted" (they are not lost silently) and can be run again.
  • Sign-in is off by default. Decisions are then recorded under the fixed name local-analyst, so "approved by a named person" only identifies a real person when sign-in is turned on (Section 6.5).
  • The status of the optional Claude summary service only reports whether a key is configured; it does not contact the service.
  • The public OpenStreetMap servers are sometimes slow or overloaded; AegisEO tries three servers and reports a missing factor if all fail.
  • The free Hugging Face deployment has temporary storage: checks disappear when the space restarts.
  • The TypeScript build-information file frontend/tsconfig.tsbuildinfo is committed to Git and changes on every build; it could be removed from version control.
  • The changes of this round have not yet been committed to Git; the new files (for example frontend/src/lib/limits.ts, frontend/src/components/map/expand.tsx, frontend/src/data/, the PNG icons and docs/deliverables/) must be added in that commit.
