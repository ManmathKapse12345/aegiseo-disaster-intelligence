Chapter 13Important implementation concepts, with code

This chapter explains the ideas that make AegisEO work, each with a short excerpt of the real code (shortened only where marked with ...). The aim is to understand the design, not to read the program line by line.

13.1 The common grid and the pixel budget

Every check starts by building one grid in the UTM zone of the area. If the area would need more than the pixel budget, the pixel size grows in 10 m steps until it fits. This one loop is the origin of the "30 m above about 1,040 km²" behaviour of Chapter 7.

# backend/aegis/geo/grid.py - Grid.for_aoi (shortened)
res = float(resolution_m)                       # 20 m unless the user changed it
while True:
    x0, y1 = math.floor(minx / res) * res, math.ceil(maxy / res) * res
    x1, y0 = math.ceil(maxx / res) * res, math.floor(miny / res) * res
    w, h = int(round((x1 - x0) / res)), int(round((y1 - y0) / res))
    if w * h <= max_pixels:                     # 2,600,000 by default
        break
    res = math.ceil(res * math.sqrt((w * h) / max_pixels) / 10.0) * 10.0

13.2 The flood model: two branches and a gate

A simple way to use two sensors is to stack all their bands as one input (early fusion). AegisEO's model instead has two separate encoders, one for radar and one for optical, and joins their features at each of four scales with a gate: a small learned network that outputs, for every pixel, a number g between 0 and 1 saying how much to rely on radar. The gate also receives each sensor's validity mask (1 where the sensor has a usable observation, 0 under cloud or outside the image), and two hard rules are built into the formula: where the optical image is invalid only radar is used, and where radar is invalid only optical is used. The network therefore cannot "hallucinate" from cloudy optical pixels.

# backend/aegis/ml/models.py - GatedFusion.forward
both = torch.cat([f_sar, f_opt], dim=1)
g = torch.sigmoid(self.gate(torch.cat([both, v_sar, v_opt], dim=1)))  # learned reliance on radar, 0..1
g_eff = v_sar * (g * v_opt + (1.0 - v_opt))  # no optical: radar only; no radar: optical only
fused = g_eff * f_sar + (1.0 - g_eff) * f_opt + (v_sar * v_opt) * self.joint(both)
return fused, g_eff

The finest-scale gate is returned as the "Radar or optical?" map layer, so a user can see which sensor the model relied on. Version 2 of the model (the one deployed) was trained with strong sensor dropout: in 30% of training examples the optical input was removed entirely and in 10% the radar, and simulated clouds covered up to 100% of the optical image, forcing the network to cope with missing sensors. It has 1,185,973 parameters and trained for 40 passes over the data (epochs), keeping the version from epoch 30, which scored best on the validation set, in about 17 minutes.

One further difference between training and use had to be bridged. The training images are Sentinel-2 Level-1C (reflectance at the top of the atmosphere) and Sentinel-1 sigma-nought backscatter, whereas AegisEO reads Level-2A surface reflectance and terrain-corrected gamma-nought. The radar values are converted to sigma-nought with a fixed −1.1 dB (the factor for an incidence angle of about 39°), and during training the brightness of the inputs was varied at random (±10% gain and ±0.02 offset per optical band, ±1.5 dB for radar), so that the model tolerates the remaining difference. Safety check G11 flags areas whose inputs still look unusual (docs/data.md, docs/failure_analysis.md).

Where only radar observed a pixel (for example under total cloud), the deployed system blends in the output of a separate radar-only U-Net, the "specialist", which performed better than the fusion model in that situation on validation data. This combination, called the hybrid, was selected automatically by python -m aegis.ml.evaluate as the configuration with the best average IoU across four conditions (both sensors, 50% cloud, no optical, no radar) on the validation split, so the test and Bolivia results remain unbiased (models/selection.json).

13.3 Calibrated probability and uncertainty

During use, the model runs on overlapping tiles of the area. For each tile, the last layer is evaluated several times with different random channels switched off (Monte-Carlo dropout), each output is divided by the temperature T (calibration) and turned into a probability with the sigmoid function (which maps any number to the range 0-1). The mean of the passes is the probability; the spread is the uncertainty. The random switches come from a generator seeded per tile, so the same input always gives the same result.

# backend/aegis/ml/inference.py - WaterSegmenter._predict_model (shortened)

gen.manual_seed(1_000_003 + ti)                        # reproducible per tile

pst = torch.sigmoid(head(feats * keep / (1.0 - p_drop)).float() / self.temperature)[:, 0]
...
pm = pst.mean(0).cpu().numpy()                         # probability (mean of the passes)
p2 = (pst**2).mean(0).cpu().numpy()                    # for the spread: std = sqrt(E[p^2] - E[p]^2)

Each guardrail returns a GuardrailResult with a code, outcome, message, measured value and threshold. The orchestrator records every result and turns "warn" into a note and "escalate" into a finding. Because the thresholds are constants and the functions take plain values, each one is unit-tested directly (backend/tests/test_guardrails_tools.py).

13.6 The tool executor: the agent cannot act on the world alone

# backend/aegis/agents/tools.py - ToolExecutor.call (shortened)
tool = self.tools.get(name)

    raise ToolBlockedError(f"tool {name!r} is not registered")

    raise ToolBlockedError(f"tool {name!r} requires human approval")  # external effects need a person
if self.stats.calls > self.policy.max_calls:                     # 120 calls per check
    raise ToolBlockedError("tool-call budget exhausted")
self.recorder.check_cancel()                                      # cooperative Stop
value = tool.fn(**kwargs)                                         # every call is timed and recorded

The default policy allows only read_only, compute and write_draft tools. The only external tool, publish_alert, can run only when an approval value is passed, and only the human approval route (decide_alert in actions.py) passes one: the approver's name.

13.10 The expandable map (new)

The map is never re-created when it is expanded, so zoom, layers and the selected square are kept. A CSS class fixes the map's container to the whole window (above the top bar, below dialogs), the page behind is prevented from scrolling, and Escape returns to normal size. The map library notices the new size on its own. One subtle bug had to be fixed for this to work: the pages' entrance animations kept a final transform after they finished, and in CSS any ancestor with a transform becomes the reference box for position: fixed, which would have trapped the "full-window" map inside the page. The animations now use animation-fill-mode: backwards, which leaves nothing behind once they end.

/* frontend/src/styles/global.css */
.map-frame.map-expanded { position: fixed !important; inset: 0 !important; z-index: 80; ... }
body.map-is-expanded { overflow: hidden; }
