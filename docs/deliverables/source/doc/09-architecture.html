Chapter 9Technical architecture

AegisEO is a two-part web application: an interface that runs in the browser and a server program that does the analysis. This chapter explains the parts, how they talk to each other, and why the system is built this way.

9.1 The big picture

A web application is a program used through a web browser. It is split between a client (the browser, which shows the interface) and a server (a program on a computer that stores data and does the heavy work). The code that runs in the browser is called the frontend; the code on the server is the backend. In AegisEO the frontend lives in the frontend folder and the backend in the backend folder.

The two parts communicate through an API (application programming interface): a fixed set of requests the server understands. Requests travel over HTTP, the protocol of the web, and data are exchanged as JSON (JavaScript Object Notation), a simple text format of named values and lists. AegisEO's API follows the REST style: each kind of thing has a web address (an endpoint), and the HTTP method says what to do with it, for example GET /api/analyses/{id} reads one check and POST /api/analyses creates one.

9.2 The frontend (browser side)

The interface is a single-page application (SPA): the browser loads one HTML page and a JavaScript program once, and from then on the program redraws parts of the page itself and fetches data from the API, instead of loading a new page from the server for every click. It is written in TypeScript, a version of JavaScript in which every value has a declared type, so many mistakes are caught before the code runs.

  • React builds the interface from components: reusable functions that turn data into a piece of the page (for example ReviewCard draws one finding with its buttons). When the data change, React updates only what changed on screen.
  • React Router maps web addresses to pages (/check, /results/:id, /review ...) in frontend/src/App.tsx. Old addresses from the first version redirect to the new pages.
  • TanStack Query fetches data from the API, caches it, and refetches it on a schedule (frontend/src/api/hooks.ts). Running checks are re-read every 2 seconds, which is how the progress bar moves; this repeated asking is called polling.
  • MapLibre GL draws the interactive maps with the computer's graphics hardware (WebGL). Background maps come from OpenFreeMap and EOX (Sentinel-2 cloudless 2020).
  • A plain-language layer turns backend values into sentences: lib/meta.tsx holds the vocabulary (names, safety-check explanations, statuses), lib/plain.ts builds sentences from real numbers, and lib/limits.ts reads the server's limits from /api/config.
  • Vite is the build tool: during development it serves the code with instant reloads and forwards /api requests to the backend; for production it bundles and compresses the code. Pages other than Home are loaded only when visited, so the large map library (about 285 kB compressed) is not downloaded on the first visit; this is code splitting.

9.3 The backend (server side)

The backend is a Python program built with FastAPI, a web framework (a library that handles the common work of a web server, such as receiving requests, routing them to the right function and sending responses). It is started by Uvicorn, the program that listens for network connections. The application is assembled in backend/aegis/main.py:

  • Routers group the endpoints: api/routes_analyses.py (creating checks, results, layers, reports, priority changes), api/routes_review.py (findings and warnings), api/routes_system.py (health, data sources, live alerts, case studies, place search, archive check, configuration, model, knowledge base, dashboard). About 37 API endpoints exist in total.
  • Validation: every request body is described by a Pydantic model (api/schemas.py), a class that declares each field's type and allowed range. Invalid or unknown fields are rejected with HTTP 422 before any code runs.
  • Middleware (code that runs around every request) attaches a request identifier, applies rate limiting (at most 240 changing requests per minute per client by default, otherwise HTTP 429), adds security headers, and records timing for monitoring.
  • Errors always come back in one shape, {"error": {"code", "message", "request_id"}}, so the interface can turn them into plain advice.
  • Access control (api/deps.py): when sign-in is enabled, requests carry a bearer token (a secret access code sent in the Authorization header) that maps to a user and role; endpoints declare the role they need.
  • When a built frontend exists in frontend/dist, the backend also serves it, so one process can host the whole application (used by the tunnel and Hugging Face deployments).

9.4 Background jobs

A check takes minutes, far longer than a web request should wait. So POST /api/analyses only stores the request (status queued), hands its identifier to the job manager (backend/aegis/jobs.py) and replies at once. The job manager runs checks on a thread pool: a fixed number of threads (independent lines of execution inside one program), two by default (AEGIS_WORKER_THREADS). Python normally lets only one thread run Python code at a time (a mechanism called the global interpreter lock), but the heavy numerical libraries used here (NumPy, GDAL, PyTorch) release that lock while they compute, so two checks really do run in parallel.

The database row of a check is the single source of truth. If the server restarts, queued checks are submitted again and checks that were running are marked interrupted, so nothing stays "running" forever. A person can press Stop: the request sets a flag that the agent checks between steps (cooperative cancellation).

9.5 The agent

The analysis is organised as an agent (introduced in Section 1.3). Its parts are in backend/aegis/agents:

PartResponsibility

memory.py		Earlier checks of the same area and their corrections; the method knowledge base with TF-IDF search.
Narrative

Recorder
recorder.py		Writes every step, tool call and safety check to the database: the "full step-by-step record" in the interface.

The decisions are made by documented rules (eight rules numbered P0 to P9, with P6 and P7 unused: coarsen the grid if too large, take the earliest radar pass, choose the clearest optical image, extend the search, match radar orbits, re-run radar-led under heavy cloud, continue without a failed source, use built-up land when population fails), not by a language model. This makes runs repeatable and every choice explainable. A language model is used only, and only if a key is configured, to word the summary; its draft is accepted only if every number and citation passes the same checks as the templates (G16, G17), and it never sees images or produces measurements. On the copy used for this report no key is configured, so all text comes from the templates.

9.7 Data access and reliability

Every call to an outside service goes through a resilient HTTP client (backend/aegis/net/http.py) with these protections:

  • Timeouts and retries: a request that hangs is abandoned; temporary failures are retried a few times with growing, randomised waits (exponential back-off with jitter), so many clients do not retry at the same moment.
  • Circuit breaker: after repeated failures of one service, further calls fail immediately for a minute instead of waiting for timeouts, like an electrical breaker that trips to protect the circuit.
  • Cache: answers are stored on disk for a time that depends on the source (for example 24 hours for OpenStreetMap, 30 days for WorldPop totals). If a service is down, the last good answer can be used and is flagged as stale.
  • Offline mode (AEGIS_OFFLINE=true): no network at all, cached data only (used by the automated tests).

Satellite images are read with rasterio, a Python library built on GDAL (the Geospatial Data Abstraction Library, the standard engine for reading and reprojecting geographic images). Only the window covering the area is read, warped directly onto the analysis grid, and saved as a GeoTIFF in a cache keyed by image, band and grid, which is why repeated checks of the same area take seconds.

9.8 Storage

Results are stored in a relational database: data organised in tables of rows and columns that can be queried with SQL (Structured Query Language). The code does not write SQL by hand; it uses SQLAlchemy, an object-relational mapper (ORM) that maps Python classes (in backend/aegis/db.py) to tables. The same code works with two database engines:

  • SQLite, a database stored in a single file (data/aegis.db), used by default because it needs no installation;
  • PostgreSQL with the PostGIS extension (which adds geographic types and spatial indexes), used in the Docker deployment. When PostGIS is present, AegisEO adds geometry columns with spatial indexes automatically.

There are 13 tables: analyses, agent_steps, tool_calls, guardrail_checks, observations (images used), detections (detected polygons), priority_cells, exposed_features (facilities and settlements), alerts, review_tasks, reports, audit_log and benchmark_runs. Files (map layers, GeoTIFF exports, PDF, CSV, GeoJSON) are stored under data/artifacts/<check id>, and downloaded image windows under data/cache.

9.10 Monitoring and security

  • Logs are written as structured JSON lines with the request and check identifiers.
  • Metrics: /metrics exposes counters and timings (requests, tool calls, safety-check outcomes, jobs, external calls) in the format of Prometheus, a common monitoring system. /api/health/ready reports whether the database and model are ready.
  • Security: optional sign-in with roles; rate limiting; strict input validation; file downloads protected against path traversal (tricks such as ../ in a file name that try to read files outside the allowed folder); a content-security policy (CSP) that tells browsers which sources the page may load scripts and images from; secrets only in environment variables and never in the frontend or logs; and the failure-injection switch used by tests is refused for real checks.
